# AI Model Gateway 管理平台

**案例類型：真實工程專案的公開化說明。**名稱、網址、帳號與數值皆以通用或合成內容取代；此頁描述系統設計與程式責任邊界，不宣稱特定環境目前可用。

## 背景與問題

當多個應用團隊共用模型服務時，平台管理者需要集中維護模型、工作區、存取範圍與使用狀態。若管理介面把平台管理憑證交給瀏覽器，或讓所有應用流量都經過同一管理服務，責任界線便會模糊，也增加憑證和流量管理的風險。

這個專案以 Flask 建立 Gateway 管理控制面，管理既有 LiteLLM 原生物件。模型推論仍由各應用使用各自設定的推論端點；管理面不代理聊天或 OCR 推論請求。

## 架構與資料權威

管理介面處理登入後的管理操作、輸入驗證、狀態呈現與操作記錄。後端以管理 API 憑證呼叫 LiteLLM 管理端點。LiteLLM 的原生 Team、模型目錄及其授權設定仍是對應平台物件的權威來源；本地資料庫保存應用自己的工作區對照、操作追蹤及其他 UI 狀態，不複製一份可衝突的模型目錄。

工作區對應原生 Team。平台管理者可管理 Workspace 與模型端點；工作區管理流程則呈現申請、核准、設定確認和存取狀態。Gateway 是否已同意申請、原生 Team 的模型 allowlist 是否已確認，以及推論執行期是否已驗證，是三種不同狀態，介面不能把其中一種當成另外兩種。

```text
管理者 ──> Flask 管理 UI/API ──管理 API──> LiteLLM 原生物件
應用程式 ──> 獨立設定的推論端點 ──推論──> LiteLLM / 模型供應端
```

此圖說明邏輯邊界。它不代表某個環境的網路拓樸或部署實況。更多細節見[平台總覽圖](../assets/diagrams/platform-overview.html)及[操作復原圖](../assets/diagrams/gateway-recovery.html)。

## 主要流程

1. 管理者建立或更新平台模型端點，系統先驗證供應商及必要欄位，再透過管理 API 變更原生模型物件。
2. 使用者在工作區提出模型存取申請；管理者核准後，平台仍須確認原生 Team 上的模型可用範圍。
3. 應用程式使用自己的推論設定呼叫模型。管理 UI 顯示已配置的入口和狀態，不接收推論內容。
4. 遠端寫入遇到逾時或回應不明時，介面保留「未知／待確認」等狀態，提供讀回或 reconciliation 流程，避免把傳輸失敗直接當作遠端操作失敗或成功。

## 設計取捨

- **保留原生資料權威。**模型定義和 Team 狀態由 LiteLLM 原生 API 維護，避免本地副本失去同步。
- **分開管理和推論。**管理端憑證只由後端使用；應用推論使用另一組部署設定與端點。
- **把不確定性呈現出來。**分散式操作可能在遠端成功、回應卻遺失。操作紀錄和復原流程保留這種中間狀態；讀回時比對操作識別、操作者、payload 指紋和原生物件識別，吻合後才確認發佈，否則仍維持未知並由人員處理。
- **明確區分核准與可用性。**核准本身不保證 Team 的原生模型 allowlist 與推論端執行設定已完成。

## 邊界與後續驗證

本案例展示管理控制面的責任範圍和可復原操作設計。它不提供真實使用量、節費、延遲或可用率數據，也不證明某項管理操作在目前環境已完成端到端驗收。使用狀態資料需依各來源更新情形判讀。

## 公開互動示範

[開啟 Gateway 操作示例](../demo.html?module=gateway)。在「分配與限額」選擇 Workspace 與模型並按「核准」，可建立獨立的核准紀錄；返回「模型與授權」後，選用已核准模型會呈現原生 Team 狀態。勾選「展示情境：模擬回應逾時」可查看「待核對」與讀回流程。核准、原生 Team 選用及 Runtime 驗證分別顯示。頁面使用合成狀態，不連接 Flask、LiteLLM 或模型端點。

此 checkout 另含可執行的本機 Flask/SQLite 重建版，提供 Workspace／模型目錄、核准紀錄、provider 選用及操作讀回；這是公開版程式，不代表原私人服務或遠端部署已隨本 repo 發佈。離線 `demo*.html` 則是獨立的合成介面，不會呼叫 runtime。若設定 LiteLLM 管理端點，公開 runtime 才會呼叫該操作者提供的服務。

# Financial OCR：把欄位帶回文件來源

**案例類型：真實工程專案的公開化說明。**所有文件、欄位值、名稱與網址均為合成或通用示意，並非真實文件或客戶資料。

## 問題

多頁財務文件的欄位需要逐頁擷取，再按案件規則整合。只留下最後一個總數，會使人難以追查欄位來自哪份文件或哪一頁；將完整原文送到雲端模型，也會增加不必要的資料暴露。

系統把文件處理拆成兩個階段：第一階段逐張影像擷取文件欄位；第二階段再彙整同一案件的已允許欄位。這不是把模型輸入切成文字 token，也不代表資料已匿名化。

## 兩階段流程與信任邊界

```text
上傳 PDF 或影像
  → PDF 頁面轉為影像
  → Stage 1 VLM 擷取欄位與文字
  → 個資識別、文件範圍代碼化、加密保存對照
  → 依已發布 Profile 篩選欄位及來源頁次
  → Stage 2 分析器回傳受限格式結果
  → 型別／Profile 規則檢查與人工核對
```

Stage 1 的影像會先交給所選的 VLM Provider，再進行 tokenization。系統可設定 OpenAI 相容的 on-prem VLM；只有當執行時確實選用可連線的本機端點，第一階段影像才留在該本機服務邊界內。具備 on-prem 設定能力不能推導出所有實際執行都在本機。

系統為辨識到的個資建立文件範圍的可逆代碼，並將解碼對照以 AES-GCM 加密保存；授權檢查與稽核記錄由流程層處理。這是具權限控制的假名化／資料最小化措施，並非不可逆匿名化。代碼能在單份文件的工作流程中維持必要關聯，不應用不同文件間代碼的相同與否推斷身分。

Stage 2 只接收已發布 Profile 白名單允許的欄位與來源頁次。遇到未對應的敏感欄位、Profile 未發布或欄位格式不符時，流程會阻止送出或回報錯誤。模型回傳會按預期 schema 與 Profile 規則檢查；這表示驗證結構與允許值，不表示系統在本機重新計算或證明了模型的完整推理正確。

## 人工核對點

- 欄位缺漏、文件類型不明或來源頁次不完整時，結果需要人員核對。
- 多份佐證可能指向同一資料；是否合併依已定義規則處理，不單憑文字或金額相同就去重。
- 模型輸出通過 schema 驗證，只表示格式符合契約；仍須按業務規則審核內容。
- 需要還原代碼時，由授權流程記錄操作並讀取加密對照；不在一般展示或紀錄中顯示原始敏感值。

## 取捨與限制

兩階段設計將原始文件辨識與案件層級的欄位分析分開，減少第二階段需要的資料並保留來源線索。加密代碼對照需要妥善管理金鑰和存取權限；Stage 1 仍會讓所選 VLM 看到原始影像。Profile/schema 驗證能攔截格式和規則錯誤，不能取代人工審查，也不構成辨識準確率或財務決策品質證據。

## 公開版 runtime

公開本機 runtime 以 RapidOCR 在本機 CPU 處理上傳圖片並加密保存文件紀錄。若選用 VLM，未修改的原始圖片會送到操作者設定的 vision endpoint，VLM 收到圖片前不會先去識別化。LLM 評估只傳送欄位白名單 profile；姓名和帳號以文件範圍 HMAC token 取代，且不含原圖、OCR 原文或來源識別資料。外送 token 是可連結的假名化資料，不是匿名化資料；本機加密 vault 另行保存文件紀錄，可供授權流程還原本機記錄，模型輸出不會自動 detokenize。離線 `demo*.html` 只展示固定合成狀態，不會執行 OCR。
